# 企微伴侣 Agent 深化评估 v2 — 架构/性能/代码结构/工具效率/提示词（v1.0.344 基线）

> 接续 `docs/agent-evaluation.md`（v1，七维度+P0 已落地 v1.0.344）。本篇基于**实测数据**与上轮未覆盖的模块（llm_client 流式管线、wecom_bridge/cdp_client、executors、registry、skills），给可复核的量化结论。
> 数据来源：`tmp/metrics.py`、`tmp/skills_break.py` 实测（全技能开启态）。

## 核心量化发现（本篇最重要结论）

每轮请求的**固定基础载荷**（不含任何对话内容）：

| 组成 | 字符数 | 占比 |
|---|---|---|
| 技能提示词（29 个技能全开） | 22,479 | 47% |
| 工具 schema（42 个） | 19,675 | 42% |
| SYSTEM_PROMPT | 4,025 | 8% |
| 窗口上下文（可选，最大 ~6K） | ≤6,000 | — |
| **合计** | **≈52K chars ≈ 17K tokens** | |

而压缩阈值 `CONTEXT_COMPRESS_THRESHOLD = 40,000`——**基础载荷本身就超阈值，对话余量仅约 -12K~6K 字符**。叠加工具结果单条上限 20K：任何一次 `read_wecom_page` 都会把对话挤爆。后果链：

1. 压缩器从任务第 1-2 轮起**永久满负荷运转**（每轮全量求和+折叠+截断）
2. 小模型的工作记忆被 11.6K 的考试/学习 SOP（与当前任务多半无关）+ 19.7K 工具 schema 挤占——指令遵循率下降的直接来源
3. `KEEP_RECENT_MSGS=8` 的实证调优是在"地基超载"下做的补偿，治标

技能提示词大头：`exam-solver 7,322` + `study-solver 4,311` = 两人占全包一半；长尾 24 个技能合计仅 ~5K。

## 一、架构设计

**现状（优点）**：分层干净——agent 核心（零 Flask 依赖）/ agent_tools / routes / wecom_bridge / llm_client 单向依赖；加工具=注册表+执行器+技能挂载三处；连接器即插即用；双模型（judge 升级）是同类本地 Agent 少有的设计；所有熔断/续跑机制有真实事故背书。

**问题**：
1. **上下文预算没有全局规划者**——系统提示词、技能提示词、工具 schema、窗口上下文、压缩阈值五方各自为政，无人对"每轮基础载荷 ≤ 模型窗口的 X%"负责（上面 52K vs 40K 就是失职现场）
2. `chat_states` / `_abort_flags` / `AUTO_LOOP_STATES` 三处进程内全局态，重启全丢（评估 v1 已提断点落盘）
3. 双模型分工只在"卡住升级"与"ask_judge"两个点接入，规划/审查（team）默认关——大模型能力利用率低
4. study_engine（633 行）与 agent_loop 是两套并行的任务循环，批量/续跑语义各有微差

**改进方向**：引入"上下文预算器"——build_chat_messages 组装时按 `模型窗口 × 系数` 分配配额（系统 X% / 技能 Y% / 工具 schema Z% / 对话余量 W），超配额的技能自动降级为"技能名+一句话摘要，按需 request_skill 加载"（该机制 v1.0.317 已存在，只差预算触发）。
**预期效果**：对话余量 6K → 30K+；压缩频率↓约 80%；小模型长任务准确率显著↑（单点收益最大）。**难度：中**。

## 二、性能表现

**现状（优点）**：流式管线成熟（泵线程+5s 轮询+四层熔断+socket 硬杀防 CLOSE_WAIT）；并行读工具 ≤4 线程；增量字符计数避免每轮 O(n) 扫描。

**问题**：
1. **CDP 无连接池**：每个工具调用 `_open_ws` 新建 WebSocket 用完即弃（`_cdp_eval`/`_cdp_command` 均如此），一次 `read_page` 内部 1-3 次 eval = 1-3 次握手。百轮任务 × 3 调用 ≈ 300+ 次握手，每次 10-50ms ≈ 每任务白耗 3-15s，外加 CLOSE_WAIT 风险（连接对象已有心跳线程，具备常驻条件）
2. 永久压缩带来的隐性 CPU：每轮全量 json 解析（高价值摘要）+ 列表重建 + 字符求和，长任务数百轮的纯开销
3. LLM 重试固定 `time.sleep(1)`，无指数退避；服务端过载时 2 次重试同样打满
4. 多 pane 并发无全局 LLM 闸门（v1.0.287 空转事故的诱因之一）

**改进方向**：per-target 常驻 WS（带现有心跳+失败重建，串行复用即可，工具调用本就基本串行）；压缩阈值改为"基础载荷 + 对话预算"动态计算；LLM 重试指数退避+抖动；全局信号量（`threading.Semaphore(2)` 级别）。
**预期效果**：单工具调用延迟↓30-60ms（百轮任务省 10-45s）；压缩 CPU 开销↓；过载空转事故复发率↓。**难度：连接池中、其余低**。

## 三、代码结构

**现状（优点）**：session.py 集中管理阈值常量（带事故依据注释，范本级）；命名与注释质量高；"逐字迁移+函数内状态原样"的迁移纪律让回归风险可控。

**问题**：
1. `loop.py` 已长到 752 行：主循环 + 三路熔断状态机（6 个计数器 3 个 warned 标志内联）+ 断点恢复摘要提取 + auto_loop 链 + 成本汇总，全部塞在 `agent_loop` 一个 600+ 行函数里
2. 三段干预消息（写循环/读循环/err 循环）结构雷同，~90 行重复，改一处漏两处的风险
3. 熔断逻辑**零单测**（132 测试全在 llm_client/工具/路由层，loop 内部行为只能靠人工长任务验证）
4. `core_utils.py` 913 行已成杂物间（日志/路径/配置/OCR/进度/记忆混杂）；`routes/management.py` 832 行
5. 干预消息与 SYSTEM_PROMPT 规则双处维护（关页守则在 loop 里整段注入，prompt 里也有浓缩版）——漂移风险

**改进方向**：抽 `LoopGuard` 类（签名/阈值/计数/干预为一体，阈值可注入）→ 可单测（模拟事件序列断言 warn/kill 边界）；三段干预合并为参数化模板；`core_utils` 按域拆分（log/fs/config/ocr）；干预话术收敛为单一来源。
**预期效果**：熔断策略可回归测试（改阈值不再靠人肉长任务）；后续"升级式再干预"等策略有落点；维护成本↓。**难度：Guard 类中、拆分低-中（纯重构）**。

## 四、错误处理机制

**现状（优点）**：v1.0.344 已落地错误码结构化（stream_interrupt/http_error/aborted/server_error）+ finish 二段校验 + 进度仪表 + 成本汇总；断点续跑/自动重试/审批挂起完备——已是强项。

**剩余问题**：
1. 熔断干预一次性（`loop_dup_warned` 置位后不再第二次干预，直通 kill）——干预话术固定，第二次没有新信息
2. judge 升级 per-tag 一次：同类二次卡住（更强信号）反而不再升级
3. 工具级超时预算不可见：单工具耗时有日志，但"本轮最慢工具/超时次数"无聚合
4. `close()` 语义不一致：`_save_chat_state` 在 error/finish/超限各路径都调用了（好），但 abort 路径不保存断点（用户主动停，合理——设计如此，记录备查）

**改进方向**：干预升级阶梯（第一次引导换方式 → 第二次直接代执行恢复动作如 close_page/reset pick）；judge 按卡住事件计数升级；慢工具聚合进 v1.0.344 的 task_summary。
**预期效果**：自愈率↑，"终止等人工"次数↓；task_summary 数据让慢工具优化有靶子。**难度：低-中**。

## 五、工具调用效率

**现状（优点）**：读工具并行、单 JS 大提取（read_page 一次 eval 拿全页）、ask_judge 缓存、结构化错误回灌。

**问题**：
1. CDP 连接churn（见性能节）
2. `TOOL_RESULT_MAX_LEN=20000` 一刀切：read 页面快照 vs list 窗口（几百字）同上限；大快照截断靠压缩期 `_shave_tool_results`（4K）兜底——信息损失点
3. 同签名重复读无去重（系统鼓励"每步 read 确认"，同页连读全价计费+全量入上下文）
4. 工具 schema 描述偏长（wecom_run_js 863 字符、run_rule_check 834），42 个合计 19.7K

**改进方向**：结果上限按工具分级（read 快照 20K 保留 struct+引用落盘路径；list 类 2K）；read 去重（页面内容 hash 命中→返回"页面未变化"摘要）；schema 描述瘦身（示例挪进技能 prompt，按需加载）。
**预期效果**：上下文占用↓（同页二读省 ~95%）；token 成本↓；截断信息损失↓。**难度：低-中**。

## 六、提示词质量

**现状（优点）**：4K 主 prompt 信息密度高；每个技能 prompt 有明确 SOP；干预消息具体可执行（"先 read 再决定"式引导而非空洞警告）。

**问题**：
1. **全量常驻**（量化见核心发现）：与任务无关的 7.3K 考试 SOP 对闲聊任务是纯干扰
2. 主 prompt 与技能 prompt 职责有重叠（并行纪律在主 prompt、批量守则在主 prompt、关页守则在技能+loop 三处）
3. 无 prompt 回归评测：改 prompt 的验证方式=跑一次真实长任务（成本高、覆盖窄）
4. 模板/快捷入口生成 prompt（1.1K each）与主 prompt 风格不一致（JSON 协议 vs 自然语言）

**改进方向**：场景包装配（v1 评估 P1-7 的具体化：入口任务直接绑技能提示词；对话任务按用户消息关键词匹配 top-1 场景包，其余技能折叠为名字+一句话）；主 prompt 收敛为"角色+通用纪律+工具规范"三节；建 10-20 条场景断言集（用 headless 驱动 agent_loop mock 跑）。
**预期效果**：对话余量释放 10-20K；无关 SOP 干扰消除；prompt 迭代从"赌"变"测"。**难度：中**。

## 实施顺序建议

1. **#2 压缩阈值动态化**（半天，立竿见影止血）→ **#1 预算器+技能注入**（2-3 天，本篇最大收益点，把 #1 拆两步：先入口任务绑定，后对话关键词匹配）
2. **#5 read 去重 + #6 干预去重**（各 0.5-1 天）
3. **#3 CDP 连接池**（1-2 天，注意串行复用避开线程安全坑）与 **#4 LoopGuard**（1-2 天）并行推进
4. P2 按需插队，#10 评测集建议与 #1 同步建设（用同一套 mock 驱动）
