# 企微伴侣 Agent 系统设计评估（v1.0.343 基线）

> 评估对象：`agent/`（loop/context/messages/session/team/sys_prompts）、`agent_tools/`（registry/dispatch/executors/skills）、`llm_client.py`、`memory_ops.py`、`skill_evolve.py`。
> 方法：通读实现 + 结合已内化的实证调优记录（压缩阈值/recent=8/导航白名单等均有一线事故依据）。

## 总评

这是一个**实战淬炼型单循环工具 Agent**：死循环三路熔断、finish 预提交校验、judge 难度升级、上下文结构化压缩、断点续跑、SSE 瞬态自愈、并行读工具、按需技能安装——大量机制有真实事故背书，工程韧性在同类本地 Agent 中属上乘。
短板集中在「**组织方式**」而非「机制缺失」：提示词单体化、工具全量注入、记忆平铺注入、压缩有损无语义、规划靠提示词模拟、**无成本核算数据**。以下按维度展开。

---

## 1. 系统提示词与角色定义

**现状**：`sys_prompts.py` 主 SYSTEM_PROMPT 为 82 行单体字符串（≈4.5K 字），混合角色定义、3 个场景 SOP、并行纪律、排版规范、finish 纪律、批量任务 10 条守则；快捷入口/模板各有独立 prompt；技能 prompt 按需注入（已有雏形）。

**问题**：
- 单体 prompt 全量常驻：答题纪律、批量守则对"帮我查个天气"类任务是纯噪声，稀释小模型注意力（47 工具 + 4.5K 规则同场）
- 规则间需要"解释性条款"调和（创作类先澄清 vs 执行类直接干），说明结构已到极限
- 场景 SOP（考试/财务审核/OA）硬编码在主 prompt 与技能 prompt 两处，重复且不同步
- prompt 迭代无回归评测：改动靠实战验证，坏一次要付一次任务失败代价

**优化方向**：分层装配——核心角色（固定短块）+ 场景包（exam/finance/oa/doc，按任务类型注入，可复用技能机制）+ 通用纪律；把 loop 里实证有效的干预消息（关页守则等）反哺进场景包，消除双处维护。
**预期收益**：小模型指令遵循率↑，规则冲突↓，prompt 迭代有安全网。**成本：中**。

## 2. 工具选择与调用策略

**现状**：47 实名工具按启用技能静态全量注入；并行只读（≤4 线程）+ 写串行；dispatch 统一结构化错误。

**问题**：
- 每轮请求携带全部 47 个工具 schema（数 K token/轮 × 百轮任务），且小模型工具误选率随 schema 数量上升
- 无阶段化裁剪（规划期/收尾期工具需求不同）
- `TOOL_RESULT_MAX_LEN` 一刀切截断，read 大快照可能截掉模型需要的字段
- `_PARALLEL_SAFE_TOOLS` 静态白名单，非副作用推导

**优化方向**：任务画像 → 工具子集（快捷入口天然绑定技能，入口任务只注入对应技能工具+基础集）；按工具类型分级截断（页面快照保 struct + 全文落盘引用路径）。
**预期收益**：token 成本↓30-50%，误选率↓。**成本：中低**（入口→技能映射已存在）。

## 3. 上下文与记忆管理

**现状**：三层记忆（用户规则 3KB / 长期记忆尾部平铺 ~3KB / 会话归档总结）；压缩=leading 6 + 结构化摘要 + recent 8 + 大结果截断 4K；append_progress 逐项 reset（实证有效）；断点内存态。

**问题**：
- **记忆无检索**：memory_text() 平铺最新条目，与当前任务无关的记忆照样注入，多了会误导（记忆上限 200 条，堆积是时间问题）
- **压缩有损且无语义**：普通工具结果（web_search/文件分析）压缩后只剩工具名；无 LLM 参与的语义摘要级压缩
- recent=8 按考试场景调优，对"多文件对比分析"类任务偏小（工具名各不同但 recent 一样小）
- 断点 `chat_states` 纯内存，进程重启后「继续」失效（跑课有台账弥补，常规对话没有）

**优化方向**：记忆相关性过滤注入（关键词/TF-IDF，无需向量库）；二级压缩（超阈值×1.5 时用小模型对折叠段做一次语义摘要）；recent 按消息类型密度自适应；断点落盘。
**预期收益**：长任务正确率↑、记忆不误导、重启可续。**成本：中**。

## 4. 任务规划与拆解

**现状**：team.py 规划→执行→审查流水线（默认关、审查只看最终答复文本、补跑 1 次）；批量任务靠 append_progress + 运行时干预消息硬引导（关页守则等 5 步循环注入）。

**问题**：
- 规划一次性、无执行中重规划；规划插 system 后小模型可能忽略
- **无结构化任务状态**：进度全靠自然语言注入，模型看不到"12 单已完成 7、剩 5"
- 拆解依赖模型自觉，无 plan 工具让模型显式登记/勾销步骤
- 审查者不看工具轨迹与落盘产物，只能审文本瑕疵

**优化方向**：plan_add/plan_check 结构化计划工具（进度每轮注入 system——把 append_progress 的成功模式通用化）；审查者输入加工具轨迹摘要+产物清单；批量任务自动注入进度仪表（`_last_links` 已有，只差注入剩余数）。
**预期收益**：长批量任务完成率与可观测性大增。**成本：中**。

## 5. 错误处理与异常恢复

**现状**：最成熟维度——写/读/error 三路死循环熔断（含导航白名单）、finish 校验 3 拒终止、流瞬态自动重试+断点、judge 升级、审批挂起恢复、auto_loop 台账续跑。

**问题**：
- **错误分类靠字符串匹配**（`"流式中断" in _err_text`）——文案一改即断，属脆弱耦合
- 熔断干预一次性（`loop_dup_warned` 置位后不再第二次干预，直接等 kill），干预话术固定
- judge 升级 per-tag 全局一次，任务中期同类二次卡住无第二次升级机会
- LLM 重试固定 2 次无退避分级；CDP 层重试策略散落 executors

**优化方向**：error 事件加结构化 error_code；熔断允许升级式再干预（第二次换更激进策略）；judge 升级改为卡住事件计数驱动；重试策略集中配置。
**预期收益**：自愈率↑，"终止等人工"次数↓。**成本：低-中**。

## 6. 输出质量控制

**现状**：finish 只校验表单/答题进度（代码层，好设计）；排版/模板靠 prompt；Ask 纪律注入；team 审查默认关。

**问题**：
- final_answer 本身无质量校验（空答复/敷衍/声称保存的文件不存在，均无代码检查）
- 创作类交付物生成后无自检（页数/文件大小/可打开性）
- 无输出回归测试集

**优化方向**：finish 二段校验（答复非空+含结果段+save_file 轨迹中声称的路径存在性核对）；交付物落盘后自动回读元信息注入；沉淀输出回归场景集。
**预期收益**：假完成/劣质交付↓。**成本：低**。

## 7. 执行效率与成本

**现状**：并行读、压缩省 token、judge 按需、无限次考试禁问大模型（成本意识已内化）、usage 事件已采集。

**问题**：
- **无任务级成本汇总**：有 usage 数据但无"本轮任务共 N 轮/M 工具调用/X tokens/最贵一步"的聚合视图，优化无度量衡
- **重复读页面全量计费**：系统鼓励"每步 read 确认"，同一页面反复读取每次全量入上下文（内容未变也全额）
- 多 pane 并发无全局 LLM 闸门，本地推理过载（v1.0.287 空转熔断事故即过载表现）
- tool_calls JSON 格式错误整轮重打

**优化方向**：任务级成本聚合（结束事件汇总 轮数/工具数/tokens/错误数）；页面快照内容 hash 去重（未变化→返回"页面未变化"短摘要）；全局 LLM 信号量。
**预期收益**：token/时间↓20%+，过载空转↓，优化有数据抓手。**成本：低-中**。

## 行动清单（按序执行）

1. **error_code 结构化**：`stream_llm_events` 的 error 事件加 code 字段，loop 分支改按码判断（1 天）
2. **任务成本汇总**：agent_loop 收尾事件聚合 轮数/工具数/tokens/错误数 → 日志+前端 meta（1 天）
3. **finish 二段校验**：final_answer 非空+结构检查+声称文件存在性核对（0.5 天）
4. **批量进度仪表**：每轮 meta 注入"links 总数/已 append_progress 数"（0.5 天）
5. **工具子集注入**：入口/技能匹配 → 只注入相关技能工具+基础集，其余进"可按需开启"提示（2 天）
6. **记忆检索注入**：按当前任务关键词过滤 memory 条目取 top-k（1-2 天）
7. **场景包提示词**：SYSTEM_PROMPT 拆核心+场景包，按任务类型装配（2-3 天，配回归场景）
8. **plan_add/plan_check**：结构化计划工具+每轮注入完成度（2 天）

> P0 四项合计 ~3 天，全部是低成本高确定性收益；P1 是下一个版本的主体；P2 在 P0 数据可视后再排。
