## P2 可读性：防御性裸异常 204 个

`except Exception: pass/continue` 分布：close_guard 24、batch_flow 18、study_engine 10、self_repair 9…（共 204）。

- **不建议全清**——close_guard/UI 线程里的 pass 是刻意的最后防线（v1.0.276 起的防崩溃设计），清了反而引入崩溃面。
- **建议分两类处理**：
  1. **IO/网络类**（文件写、requests、JSON 解析）：把 `pass` 升级为 `log_event(...)`（一行成本），异常不再静默。build 计数器已把"裸 except-pass"作为单调指标（当前 206），建议每轮递减 5-10 个。
  2. **UI/时序类**（CDP 探测、控件操作）：保留 pass，但统一加注释标记 `# 防御兜底：见 docs/异常兜底约定`，让读者不必每次判断"这是偷懒还是设计"。

## P2 性能：三个小点（均非瓶颈，按需做）

| 位置 | 现状 | 建议 | 触发条件 |
|---|---|---|---|
| `core/logging.py log_event()` | 每条日志：锁内 open+append+close+**stat 查大小**（轮转检查）。agent 流式时每秒可产生数十条 | 改为进程内计数器 + 每 N 条/每 10s 才做一次 stat；或换 `logging` + `QueueHandler` 后台写 | 仅当单次任务日志 >500 条时体感 |
| `services/wecom_archive.py:250` 等后台线程 | 每 30s tick 全量读 config.json（27KB） | 现状无害。若未来 config 增长 >1MB，可加 mtime 缓存（`config_store.get_cached()`） | config 超过 1MB |
| 前端 `10-chat.js`（1813 行） | 单文件持续膨胀 | 下次大改时拆出 `chat/approval.js`、`chat/ask.js`（审批卡/提问卡渲染独立） | 触碰该文件的需求到来时 |
