## 一、安全与写操作闸门（P0 集中区）

**现状（优点）**：写操作询问已收敛到 `security_ops.gate_write_tool()` 一处（`security_ops.py:185`），一次性令牌按 `(工具名 + 全参数 hash)` 发放（`:197`），审计走 jsonl 且带轮转，危险命令 / 批量删除 / 路径越界各有独立闸——这套骨架是对的，问题在**它看不见批审的真实后果**。

1. **P0 · 审批弹窗上看不出"这会真提交 N 张单据"**
   `tool_action_label()` 只取 `target/path/command/text/name`（`security_ops.py:170-182`），而 `run_audit_flow` 的参数是 `{flow, auto_approve}` → 弹窗标题只会显示"执行 run_audit_flow"，**`auto_approve:true` 完全不显形**；批准后每张 green 单据当场点「通过」（`services/batch_flow.py:1105` → `_approve_in_detail`）。影响：一次批准 = N 次真实审批提交，无单张粒度、无撤销。改进方向：把 `auto_approve` 提为独立确认，或至少让标签显式写出"将真实提交 N 张"。
2. **P0 · 默认档下模型自己就能触发真提交**
   `gate_write_tool` 仅在 `lv == "ask_every"` 时询问（`security_ops.py:195`），而 `core/config_store.py:111` 的默认值是 `"auto"` → 用户没动过设置时，模型只要肯传 `auto_approve:true` 就零询问。工具描述里那句"仅用户明确要求时传 true"（`agent_tools/registry.py:83`）是**提示词约束，不是代码约束**。
3. **P1 · 界面承诺与实现不符**
   index.html:654/658/1198 都写"每次询问 = 所有写操作动手前都弹窗确认"，但 `agent/loop.py:98-102` 对 `sched-*` / `study-*` 会话**静默降级为 auto**（有日志，界面无任何提示）。影响：用户以为夜间任务在"每次询问"保护下，实际它可自主写。
4. **P1 · `cmd` 分支仍走 shell 解释器**
   `agent_tools/os_ops.py:466` `Popen(command, shell=True)`（同函数 powershell 分支 `:460-464` 已数组化）。唯一闸门是 `check_command` 的模式表 → 绕过面取决于表的全集。**`docs/代码优化建议报告_v1.0.561.md:5/:50` 的"subprocess 零 shell=True"结论已失效。**

## 二、可诊断性：「一句笼统失败」还没清零（P1）

**现状（优点）**：v1.0.599 给批审补了栈、v1.0.608/611 给 OCR/语音做了真自检与 `last_error` 透出、守护线程统一带 traceback 尾——这类问题已经在系统性收敛，但**同型缺口还剩一大片**。

5. **工具异常只回传模型、不落日志** → `agent/loop.py:545`：`except Exception → {"__error__": "工具执行异常：…"}`，真因栈丢失。这是 v1.0.599 修过的**同一模式**，只是换了一处。
6. **94 处 `except Exception → return {"__error__": …}` 无日志**（子代理计数；抽样核实：`agent_tools/executors.py:238/595`、`wecom_bridge/download.py:462`、`agent_tools/connectors.py:66`）→ 与第 5 条同型，量大但可批量套同一修法。
7. **整块守护逻辑被 except-pass 包住** → `backend.py:213`（管理员重启看门狗）→ 提权失败根因不可追。
8. **会话解析失败静默丢条目** → `services/conversations.py:139-140`（`except: continue`）→ 列表少一条且无痕。

9. **运行状态永远不可见**：前端读 `s.running` 渲「执行中…」徽标（`js/11-workspace-kb-study.js:603`），后端**只在结束时 `x.pop("running")`**（`services/scheduler.py:250/261`），从不写 `True`（防重叠用的是内存里的 `_running_flag`，不落盘）。影响：点「▶ 立即跑」后界面毫无变化，用户会重复点。

## 五、性能与资源（P2，含"实测无代价"的诚实标注）

**现状（优点）**：requests 全带 timeout、缓存点普遍加了 TTL/锁、界面路径已在 v1.0.611 摘掉 34.6 秒的镜像往返。

18. **`list_all()` 每次全量 `json.load` 且为每条消息构造 `{role}` 数组**（`services/conversations.py:126-142`）→ 随会话数线性变差。**当前实测代价为 0**：打包会清空 `dist/产物库/会话`（本机现 0 个 json），所以这是债不是故障。
19. **同一逻辑两份**：>5MB 预览截断在 `routes/knowledge.py:64-72` 与 `routes/workspace.py:116-125` 各写一遍，阈值 `5*1024*1024` 两处独立。

**全修过程中实测抓到的新问题（不在报告里，本版一并修掉）**：
- **解不开的 DPAPI 密文差点被设置页销毁**：对着正式页跑新 UI 时，`银行账号`/`开户行` 两项在输入框里显示成 **359 字符 base64**——本机开发树的这两项解密失败（DPAPI 绑定 Windows 用户+机器，配置从别的机器/账户搬来必然如此，实测错误码 `0x8009002B`），`_unprotect_secret` 按 v1.0.590 的规矩原样保留密文。可新 UI 一旦把它下发进 DOM，保存时就会被 `_MAX` 的 48 字符限长**截断写回**——唯一一份密文就此销毁，正是 v1.0.590 立规要防的那类不可恢复丢失。现在 GET 下发空值 + `encrypted_fields` 标记，POST 遇「空值 + 存的是不可读密文」跳过该键并落日志，界面明说「留空保存不会清掉它，填新值即覆盖」，dsh 凭据同口径（`api_key_tail` 只在可读时给，密文末 4 位既无辨识意义又泄露密文片段）。锁 4 条。
- **正式包根本没有 reimburse 段**：`dist/config.json` 里 `reimburse` 为 `None`，而开发树 `config.json` 才有那三项密文——也就是说**用户真正在跑的正式包里从来没有配过报销个人信息**，`rule_check` 的报销默认值一直返回空、模型只能回头问人（正是第 29 条描述的现象，但成因比报告写的更直接）。本版给了填入口，用户填一次即可；未代为搬运（跨配置写 PII 属有后果的动作，留给用户决定）。

- **加载态按钮被对比度扫描器判成未达标（4.24:1）**：本项目的"处理中"用的是 `button.loading{opacity:.6;pointer-events:none}`，`setBtnLoading` 不置 `disabled` 属性，所以 v1.0.614 新加的"禁用控件豁免"接不住它。先归因再动规则：`pointer-events:none` 在语义上就是**点不动的失活组件**（WCAG 1.4.3 的 incidental 正覆盖这一类），于是只把豁免限定在 `button/input/a` 三类**控件**上，普通文字带 pointer-events 一律照常测——不是放宽文字判据。改后正式包复扫：2409 次采样 / 2 主题 / 3 视图 **0 findings**。

**与报告建议的偏离（有意）**：① 32 条的"文件树"只加了 `台账`/`日志` 两个**只读**段并标 `readonly`，`组件/` 不进树（7 万文件列出来是噪音，且 `_ws_tree` 只列直接子文件，组件顶层只有目录）——占盘信息改由体积口径承担；② **没有新增删除接口**：删除产物库文件需要与 `security_ops` 保护路径、回收站语义、备份前置一起设计，不是一次全修该顺手做的事，仍列在下表。③ 只读段读取**不走 `ws_sub()`**——它对不在写入名单里的段静默回退「产出」，照它读会把台账读成产出里的同名文件（这条陷阱已写成断言）。④ 新设置页自带**「没读到就别保存」闸**：GET 失败而 POST 成功时输入框是空的，直接保存等于把真实姓名/银行账号写成空值——这是本类功能最隐蔽的一种数据丢失（保存还返回成功），前端两处保存入口都拦了并有源码锁。
