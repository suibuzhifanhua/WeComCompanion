## 一、写操作安全与数据丢失（P0 集中区）

**现状（优点）**：v1.0.614 把审批闸门做成了三层——标签显形不可撤销、`_ALWAYS_ASK` 跨档强制弹确认、后台无弹窗会话直接拒绝并落日志；这条链路本身经 12 条锁验证，是全项目最结实的一块。问题在于**它只覆盖了一条通道**。

1. **P0 · 宏重放旁路整个权限体系**：重放循环直接 `dispatch_tool(c["name"], c["args"], cfg)`，无 `gate_write_tool`、无 `_ALWAYS_ASK`、无 Ask 只问答拦截 → 录进宏的「点通过/提交/发消息」在「每次询问」档也零弹窗；SSE 开跑后前端无 abort。
   证据：[routes/b_macro.py:106-121](routes/b_macro.py#L106)、[js/11-workspace-kb-study.js:111-131](js/11-workspace-kb-study.js#L111)（只有一句通用确认文案）。
   影响：用户点错宏就只能眼看它把提交类步骤跑完；批审宏重放的后果与 agent 路径同级但约束为零。
   改进方向：重放走与 agent 同一个闸门函数（含 `background=False` 的弹窗语义），并给重放加停止入口。**难度中**（要在 SSE 里挂确认回环）。

2. **P0 · 企微 webhook 被任何一次设置保存静默清空**：`GET /api/config` 把 `wecom.webhook` pop 掉不回传（防密钥外泄，正确），但 `POST` 用 `if data.get("webhook") is not None` 判定 → 前端输入框恒空（`loadWecomOpt` 读不到值）→ 用户勾一下「静默后台执行」就把 `webhook:""` 写回去，**覆盖掉已配置的机器人地址**。
   证据：[routes/b_admin.py:192](routes/b_admin.py#L192) + [routes/b_admin.py:216-217](routes/b_admin.py#L216)、[js/05-connectors-status.js:229](js/05-connectors-status.js#L229)（payload 必带 webhook）、[js/05-connectors-status.js:239](js/05-connectors-status.js#L239)（回显恒为空）。
   影响：`send_wecom_webhook` 能力莫名失效，界面上看不出任何原因（输入框一直是空的，用户以为没配过）。
   改进方向：与 dsh 凭据同口径——空串＝不动，另给显式「清除」；或 GET 回传掩码值 + POST 识别掩码。**难度低**。

3. **P1 · 自修复补丁"验证通过"后先删备份、再尝试 git 提交**：本项目源码树**不是 git 仓库**，`_autofix_git_commit` 必然失败 → 状态记 `applied`，而唯一回滚物 `bak` 已在提交前被 `os.remove` 删掉。
   证据：[services/self_repair.py:371-378](services/self_repair.py#L371)。
   影响：改错只能人工恢复；与「实验性自动代码修复」卡片承诺的"失败自动还原原文件"在**成功但不该成功**这一支上没有兜底。
   改进方向：无 git 时保留 `bak` 并在报告里给出还原路径。**难度低**。

## 二、静默失效与"保存成功但没生效"

上一轮修掉的是 `kb_auto` 写错键名；本轮抓到同族的三类。

4. **P1 · 安全正则不校验语法，写错即永久静默失效**：保存只校验"是不是字符串数组"，命中处 `except re.error: continue`。
   证据：[routes/security.py:38-44](routes/security.py#L38)、[security_ops.py:346-349](security_ops.py#L346)、[security_ops.py:372-373](security_ops.py#L372)。
   影响：用户精心写的放行/拦截规则一字之差从不生效、从不报错，安全策略呈现"保存成功"假象。
   改进方向：保存时逐条 `re.compile` 试编译，失败返回 400 并指出第几行。**难度低**。

5. **P1 · 后台会话拒绝写操作后，定时任务仍报「✅ 完成」**：闸门拒绝只回灌模型（`out = _gate`），**不发任何 SSE 事件**；调度侧 `_blocked` 只统计 `ask_user`/`approval_request` → status 落 `ok` → 通知「✅ 定时任务完成」。
   证据：[agent/loop.py:604-608 + 648-657](agent/loop.py#L648)（`if _intercepted: pass`，无 yield）、[services/scheduler.py:219-220](services/scheduler.py#L219)、[services/scheduler.py:295](services/scheduler.py#L295)。
   影响：用户最核心的「夜间自动审批」场景可能整晚一份没提交，而通知与产出文件都写着完成，唯一线索在日志里。**这正是 v1.0.614 批 3 立"后台拒绝"时留下的尾巴**。
   改进方向：拒绝计入 blocked 判据（或让 loop 发一条 `notice` 事件）。**难度低**。

6. **P2 · 两套"等新页面出现"轮询 + 两份 keep-url 名单**：`_find_new_page`（按 id/url 差分，[wecom_bridge/windows.py:284](wecom_bridge/windows.py#L284)）与 `_wait_new_page`（按标题差分，[services/batch_flow.py:710](services/batch_flow.py#L710)）；`_SILENT_KEEP_URL_MARKS`（[wecom_bridge/windows.py:845](wecom_bridge/windows.py#L845)，注释自认"与 `_KEEP_URL_PAT` 保持同步"）与 `_KEEP_URL_PAT`（[services/batch_flow.py:316](services/batch_flow.py#L316)）当前内容一字不差。
   影响：改一漏一 → 批审列表页被 tucker 误收（这条历史上有过同类事故）。与已知未做的 feature_flags 两份名单漂移是**同一种病**。
   改进方向：名单收敛到一处常量 + 源码锁禁止再抄。**难度低**。

## 三、并行会话互相干扰

7. **P1 · 弹窗按全局 id 去重，第二个会话的确认被静默吞掉**：`if(document.getElementById("skillReqModal")) return;`（[js/10-chat.js:851](js/10-chat.js#L851)）、技能源导入同写法（[js/10-chat.js:900](js/10-chat.js#L900)），另有 1368/1438 两处同型。
   影响：多会话并行（v1.0.488 的招牌能力）下，A 弹窗未关时 B 的请求既不排队也不提示，B 在后端**永久等待**，用户只看到 B 卡住。
   改进方向：按 pane 排队或把待确认数显示在会话标签上。**难度中**。

8. **P2 · 工作台与助手两个 🎤 共享单一录音态**：在 B 输入框点 🎤 会**停止** A 的录音而不是开始（[js/14-mic.js:13-14,56-61](js/14-mic.js#L13)）。
   改进方向：录音态按输入框键控。**难度低**。

## 四、口径与文案真相（含"锁本身锁错"）

9. **P1 · 我上一轮写的锁被 `<b>` 绕过，帮助页版本号数仍是错的**：`test_v614_copy_truth` 的正则 `(?:近|保留最近)\s*(\d+)` 要求"近"与数字紧邻，而 [index.html:1164](index.html#L1164) 写的是 `最近 <b>8 个版本</b>` → 不匹配 → 绿灯。代码真值 `_KEEP=3`（[services/version_store.py:22](services/version_store.py#L22)）。
   影响：用户按"8 版可回退"预期去找回滚项，实际只有 3 版；更严重的是**这条锁从此不可信**。
   改进方向：正则改成"先剥标签再匹配"，并顺手把 1164 改对。**难度低**。

10. **P1 · 新设置卡自述「纯本地汇总，不调模型」，实现默认调 LLM 扣额度**：[index.html:653](index.html#L653) vs 同卡导语 [index.html:649](index.html#L649) 与 [services/daily_digest.py:9,147-157,173](services/daily_digest.py#L147)（`_llm_md` 走 `resolve_model`，失败才降级纯数据版）。
    影响：这张卡存在的唯一理由就是"谁在耗额度看得见"，文案却把最大的那个消耗源说成不消耗。
    改进方向：改成「默认会调模型润色（LLM 不可用时降级纯本地）」。**难度低**。

11. **P2 · 「多模型自动兜底（体检/任务失败自动换备用模型）」只有体检那半为真**：[index.html:1129](index.html#L1129)；实际换模型只在自我修复里（`self_repair.py:693-752`），agent 主循环失败只提示"更换模型后重试"（[agent/loop.py:505](agent/loop.py#L505)），`llm_client.resolve_model` 是单模型。
    影响：默认模型 401/欠费时任务直接停摆，与宣传不符。改进方向：文案收窄到体检，或真做任务级兜底。**难度低/高（二选一）**。

12. **P2 · 空态与按钮文案的旧 UI 残留**：`clearChat` 空态引导「打开工作台 · 点『新建』」（[js/10-chat.js:1167](js/10-chat.js#L1167)），而用户已在工作台、入口是侧栏「＋」；「测试连接」按钮 title 写「测试当前**选中**模型」但前端恒发空 body（[index.html:278](index.html#L278)、[js/05-connectors-status.js:214-217](js/05-connectors-status.js#L214)），后端回落到**默认**模型（[routes/b_models.py:73-74](routes/b_models.py#L73)）→ 多模型用户会得出"这行模型可用"的错误结论。

### 刻意没做的两条（以及为什么）

- **6 的后半：两套"等新页面出现"轮询不合并**。`_find_new_page` 按 **targetId/url** 差分（给收纳守护用：它要的是"企微名下出现了我没见过的窗口"），`_wait_new_page` 按 **标题**差分并等新窗口导航完成（给批审用：它要的是"点开的那张详情页标题匹配上了"）。判据、超时、返回结构、失败语义都不同，合并只会得到一个两边都要 `if kind ==` 分叉的函数——**这跟名单漂移不是同一种病**（那份是同一份数据抄两处，这两处是两个不同的问题）。已在 `_wait_new_page` docstring 写明"为什么不合并"，避免下一轮审查再当新发现。
- **24：tucker 忙时 1.2s 一次全量 EnumWindows 不降频**。这是 v1.0.5xx 已记录的交易：扫描只在 **agent 任务进行中** 开启（空闲不扫），换来的是"新窗口一出现就收进后台、不在用户眼前闪"，而自动收纳窗口是用户定的红线。降频会让新窗口在屏幕上停留更久，属于**拿可感知的界面打扰换 CPU**，方向不对。真要优化应该是事件驱动（`Dev.targetCreated` 已经在推送，但企微会漏推，所以留了轮询兜底）——这条应记在"结构重构"那一档，不与其他项抢排期。

### 二、进程枚举：一条只在并发下现形、现形方式是"静默给错答案"的 bug

`wecom_bridge/wecom_proc.py` 两条进程检测各在**函数体内** `class PROCESSENTRY32`（每次调用新建一个类对象），再把 `POINTER(自己的类)` 写进**全进程共享**的 `ctypes.windll.kernel32`。单线程看不出问题（谁调用前谁覆写、紧接着就用）；而收纳守护跑在后台线程、绑定探测与重启流程跑在请求线程：A 设完签名还没调用，B 已把签名改成 B 的类，A 带着 A 的实例调用时 ctypes 按**类身份**判等。

实测复现（本机 wecom venv）：

```
ArgumentError  argument 2: TypeError: expected LP_PE32A instance instead of pointer to PE32B
```

后果分两支，都偏危险方向：`find_wecom_all_pids()` 外层是 `except Exception: return set()` → **企微进程检测静默变空**，`_relaunch_with_cdp` 据此认为"进程已经死干净"直接 Popen 新实例，Electron 单实例锁让新实例闪退（历史上"偶发绑定失败"正属这一族症状）；`find_wecom_pids()` 那支则静默回退 `tasklist` 子进程慢路径。

- 修法：一份 `_PROCESSENTRY32` + **模块私有的 `ctypes.WinDLL("kernel32")`**（函数指针缓存在实例上，不与 `windll` 共享）+ **导入期绑一次签名**，调用点不再改任何全局对象；两条入口都走同一个 `_enum_pids_named(names)`。
- 失败路径**必须留痕**：`find_wecom_all_pids` 仍按契约返回空集合（宁可不最小化，方向安全），但会记一条 `[wecom] find_wecom_all_pids 枚举异常…`；`find_wecom_pids` 回退 tasklist 时也记一条。
- 锁：共享 `windll.kernel32` 的 `Process32First.argtypes` **必须一直是 None**（改前会被写成 `POINTER(某类)`）；结构体只准有一份；6 线程 × 12 轮并发跑两条入口，既不许抛、也不许出现"枚举异常/回退 tasklist"的痕。
