## 一、架构设计与模块划分

**现状（优点）**：目录即职责，且**没有向下违例**——`core/*`、`security_ops.py` 从不反向 import `routes/services/agent_tools`（逐边核对 0 条）；`core_utils.py` 是 v1.0.402 拆分后留下的 47 行转发壳，不是新耦合源；路由层 19 文件 137 条，`routes/management.py` 做聚合注册，URL 前缀统一。

**问题**
1. 机制层与业务层混在一处：`wecom_bridge/read.py:46 click_element`、`:317 type_text` 是**写操作**，住在名为 read 的模块里，而 `wecom_bridge/act.py` 也存在 → 新增页面动作无处可放（**改进方向**：按读/写重划，或把 read.py 改名 page_actions.py）。
2. 一个文件多域：`routes/b_admin.py` 888 行 30 条路由含经验/连接器/状态/配置/用量/ASR/看板/快捷链/规则/管理员/自启 10 个域，其中 `/status`、`/admin/status`、`/dashboard` 三个"状态"端点无归属说明；`desktop/close_guard.py` 962 行装了 Win32 ABI 声明、自绘 DPI 对话框、托盘、热键 5 套职责。
3. 同一概念两处实现：`resource_path` 在 `core/paths.py:49` 与 `desktop/tray.py:53` 各一份（同为 `_MEIPASS` 解析）。
4. 一个能力散在多文件：加一个 agent 工具要同时改 5 处（`agent_tools/registry.py` schema、`executors.py` handler、`skills.py` 内置提示词里的工具名字符串、`security_ops.py` 中文标签、`agent/loop_guard.py` 只读名单）——上面「提示词指错工具」正是这条散点的直接后果。
5. `core↔core_utils` 成环（`core/config_store.py:15` 反向 import 壳），壳的存续没有期限锁。

**影响 + 难度**：1、3、4 是**中影响/低难度**（改名+合并+建单点注册表）；2 是低影响/高难度，按上一轮结论不做大规模拆分。

## 二、代码规范与可读性

**现状（优点）**：命名整体自洽，注释是「WHY + 实测代价 + 版本号」式且有价值；`version.py` 有"不要手改"的硬约定；锁文件按版本前缀组织（48 个 `test_vNNN_*` + 52 个长期锁）。

**问题**
1. `security` 一词三义：根 `security.py`（DPAPI 密钥）、`core/security.py`（单实例 mutex，与安全无关）、`routes/security.py`（安全中心 API）；`core/config.py:7` 在包内 `from security import ...` 指向根模块，与同名 `core/security.py` 视觉冲突。
2. 同名不同义：`core/idle.py:26 idle_seconds()`（HTTP 静默，无数据返回 1e9）vs `core/idle_detect.py:21 _idle_seconds()`（系统输入，失败返回 None），两个等待函数参数顺序还不一样。
3. 同文件两种错误风格：`wecom_bridge/frames.py` 既 `raise`（:41/:218/:224/:227）又 return 错误字典（:116/:118）；同包内 `wecom_proc.py` 全程 raise，`windows.py`（37 处 `__error__`）与 `download.py`（70 处）全程 return。调用方需要按模块记忆风格。
4. 魔法数无单一来源：`timeout=` 数字字面量约 130 处、`time.sleep(N)` 约 100 处；`services/batch_flow.py` 只有 :43-44 两个常量，其余 :362/:707/:915/:938 裸值，同文件内 `timeout=5` 与 `timeout=5.0` 并存。
5. 注释指向错的调用方：`agent_tools/executors.py:31 DEFAULT_MSG_TYPE` 注为「send_wecom_message 默认消息类型」，实际只被 :682 的 `send_wecom_webhook` 使用。
6. CSS 后层覆盖无约定：`button:disabled` 三处冲突声明（`css/style.css:288`、`:809`、`:1026`，分别是 opacity/filter 两套做法）、`.chatpane` 六处、`prefers-reduced-motion` 两处（:449、:785）。
7. 函数长度长尾：1116 个函数中 50-99 行 101 个、100-199 行 31 个、≥200 行 7 个（含 `agent/loop.py` 内的执行器函数）。

**影响 + 难度**：3、5、6 低影响/低难度（约定 + 一次性整理）；1、2 中影响/低难度（改名 `core/single_instance.py`、`core/http_idle.py`/`core/input_idle.py`）—— 现在每次读代码都要多花一次判断。

## 三、错误处理与边界情况

**现状（优点）**：v1.0.588 起 F821 是打包硬门禁（当前 0 条）；本轮新修的窗口枚举回调护栏 + 进程枚举私有绑定，把最隐蔽的一类静默失败堵住了；日志普遍带 `traceback.format_exc()` 尾。

**问题**

5. 死变量说明某分支白算（pyflakes 199 条里的语义项，风格噪声已剔除）：`services/batch_flow.py:954 _base_titles` 算完弃用（:958 改用 `_base_ids`）→ **每轮白跑一次 CDP 页面枚举**；`batch_flow.py:1262/1268 _resumed` 只写不读；`services/dsh_bridge.py:412 timed_out`、`services/self_repair.py:217 used`、`agent/team.py:118 _buf`（后四条来自子代理，前两条我已回源，其余为**待复核**）。

## 五、安全风险

**现状（优点）**：本机自用面收得比较紧——Host 白名单 + HttpOnly cookie token；`/api/*` 需 token；模型凭据/连接器密码只写不回显；DPAPI 覆盖密钥与报销个人信息，解密失败不把密文当明文外发；写操作三层闸门（标签显形 + `_ALWAYS_ASK` + 后台会话直接拒绝），且本轮把宏重放这条旁路补上了。

**问题**
1. 三-1 的 fail-open 是本轮唯一"高危/低成本"安全项：**token 不可用时应拒绝写操作**（只放 GET 与静态资源），而不是静默降级。
2. `wecom_run_js` 的黑名单只挡 `eval(` / `new function(`（`agent_tools/executors.py:785`），`Function("…")` 的变量别名与 `setTimeout` 非字面量参数理论上仍可绕过；该通道能带企微登录态，属"窄只读白名单 + 默认转人工"的收口对象（子代理结论，我未做绕过验证 → 记为**推断**）。
3. `agent_tools/os_ops.py` 的 `shell=True`（两轮已挂账）仍是"命令拼接"面：需要一次产品决策（改参数数组会打断现有拼接用法）。
4. 数据副作用面：默认打包把历史对话搬去 `build/_chat_archive/`（确认弹窗 `js/11:423`、`index.html:1431` 都没提），`--release/--lean` 把 `dist/config.json`+`产物库` 搬去无限累积的 `build/_release_excluded/`。不是漏洞，但"用户以为只是打包"会造成数据位置困惑；PII 告警已有（`build.py:542`），**外发纪律仍靠人记**。
5. 软件内「一键打包并重启」写死 `--yes --force`（`routes/b_repair.py:144-146`），`--force` 正是为 v1.0.209/212「误杀运行中任务」而设的守卫的旁路；且 :188 的"防空转"门禁依赖 git，本目录无 `.git` → **恒走"保守放行"**。

**影响 + 难度**：1 高/低；5 中/低（把 git 比对换成本机日志时间戳，与命令行守卫同源）；2、3 中/中（需产品决策）。

### 二、用户中途报障（另一台机器）

`❌ 打包构建环境：未找到依赖清单：<项目目录>equirements-dev.txt（软件需在源码目录结构内运行）`
归位后 exe 在 `Desktop\企微伴侣\`，源码根算出来是 `Desktop`——**正式包根本不带源码**，软件内一键打包在这类机器上做不到也不需要，却被报成"组件坏了"、还被一键安装列为待办点一次错一次。现判 `na`（不进待处理、不给安装按钮、汇总不计入分母、单独报 `na_n`），端点直连也给人话不给绝对路径。锁：`test_v619_components_na.py`（7 条，含前端三处计数逐一排除 na）。

### 三、我这条审查算错的四处（回源纠正）
1. **「`test_asr.py` 有 22 个测试从不执行」——错。** 该文件是同一份内容被整块粘了 4 遍：8 个测试名各重复 3-4 次，**每一遍的函数体逐字相同**，所以覆盖不到任何新分支，"30 声明/8 收集"是重复不是丢失。真问题是 3/4 行噪音 + 同名遮蔽让人改第一遍等于没改。已按事实修（去重，收集数仍 8）。
2. **「`_BIND_CACHE`、`agent/tools_call.py` 是死代码」——错。** 前者被 `backend:512`/`routes/wecom:59` 读写，后者被 `agent/loop.py:27` import。是子代理给的，我没回源就写进了报告。
3. **「12 条 f-string 无占位符里可能藏着漏插值」——逐条看完，11 条（现值）全是纯文本，无一处该插值。** 与 `.tag.def/.tag.dis` 那次同类：静态提示不等于缺陷。
4. **我自己第 2 批的收尾说法「实现上移后会被 `--smoke` 导到」——错。** 619 打包时冒烟只报 **9 个模块**（项目实际有 51+ 个包内模块）。根因：onefile 冻结态里 `core/`、`services/` 这些包**不以目录形式存在**（全在 PYZ 归档内），`--smoke` 用 `os.walk(源码根/<pkg>)` 拼清单，冻结下几乎扫不到东西——所以「`--smoke` 能抓 hiddenimports 漏模块」长期只在源码态成立。**这恰好是本轮那条死路能活到发货的同型原因**：我以为存在的检查其实没在跑。已改：清单优先从冻结导入器的 PYZ TOC 取（`sys.meta_path` 里带 `_toc` 的那个 finder），取不到才回落磁盘遍历；619 包则改用归档直读做人工核对（`PyInstaller.archive.readers`：PYZ 2402 个模块，`core.frontend_check` **在**、`tools.*` **为 0**），这个证据是硬的，只是它不该由 `--smoke` 名义来背。
