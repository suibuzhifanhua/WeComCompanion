## 一、架构与模块划分

**现状（优点，真实存在）**

分层是这个项目最值钱的部分：`core/`（路径/日志/配置/安全/OCR）→ `wecom_bridge/`（CDP 与 Win32）
→ `agent_tools/`（工具注册与执行）→ `agent/`（ReAct 主循环）→ `services/`（业务流）
→ `routes/`（HTTP 蓝图）→ `backend.py`（装配与启动）。依赖方向实测基本单向：
最强边是 `services→core(45)`、`routes→services(38)`、`routes→core(31)`，
**没有出现 `core→services` 或 `core→routes` 的反向依赖**（`core_utils.py` 是 2.9K 的转发壳，91 个文件依赖它，属兼容层不是环）。
`agent_tools` 只依赖 `core/security_ops/wecom_bridge`，工具层可单测；
`llm_client.py` 是全软件唯一模型出口（12 个消费者），熔断层次在文件头有索引。

**问题**

1. **入口层与路由层仍有软耦合**：`backend.py` 里既做启动装配又直接引用蓝图内部符号的历史痕迹
   （v1.0.510 已把 `_BIND_CACHE` 下沉到 `core/wecom_state.py`，但 `backend.py:1013` 仍在函数内
   重复 `import traceback`——pyflakes redefinition）。改进方向：把启动期副作用收进 `core/bootstrap.py`
   一类单一入口。收益小、难度低。
2. **三个 >300 行函数承担多职责**：`agent_loop`（953 行）同时管轮次驱动、工具派发、熔断判定、
   断点存储、收尾播报；`_stream_body`（359 行）把"发请求 / 四重熔断 / SSE 解析 / 收尾装配"写在一个
   while 里。改进方向：按已有的 `loop_guard.py`/`loop_ops.py` 形状再切一刀（把"收尾与播报"、
   "熔断泵"各自提成纯函数）。收益：这类函数正是 628/630 两个 bug 的藏身处，纯函数化后
   才能像 `_interrupt_notice/_interrupt_tip` 那样被真分支测到。难度中。
3. **口径分散**：后台会话前缀 `"sched-"/"study-"` 手抄 **5 处**（上轮 A5-3 仍成立），
   新增无人值守入口时会"权限被静默降 auto"或"断点被 LRU 回收"。改进方向：`agent/session.py`
   出 `is_background_pane(pid)` 单点。收益：消除一整类静默降级。难度低。

## 二、主要业务流程（核对过控制流）

1. **启动**：`backend.py` 单实例 mutex → Flask + pywebview（8787）→ 服务就绪探测（0.2s×60）→
   托盘 → `start_window_tucker(cdp_port)` → 另存为 watcher（默认关）。
2. **一次对话**：`/api/chat` → `build_chat_messages`（系统提示 + 企微窗口上下文 + 会话历史）→
   `agent_loop` → `stream_llm_events`（外层重试 → 并发闸 → `_stream_body` 四重熔断）→
   工具 `dispatch_tool`（安全闸门 `security_ops`）→ 结果回填 → `finish` 发 `【完成】` →
   `_memory_watch` 落库会话 + 异步记忆/技能自进化。SSE 事件是**字符串**
   （`_sse_stream` 只透传，不序列化）——这条契约 628 之前被 `isinstance(ev, dict)` 判据破坏过。
3. **月报批审**：`services/batch_flow.audit_monthly_reports` → `_open_detail`（优先
   `open_silent_page` 后台开页，失败回退前台点击）→ `read_fields` → `rule_check`
   （确定性规则 <1ms，零 LLM）→ `tuck_new_windows(baseline)` 即时收纳并归还焦点 → 报告落
   `产物库/产出/月报检查_YYYYMMDD.md`。
4. **静默收纳（v1.0.629 重写）**：`note_agent_open(开页前基线, target_id)` 登记 →
   `_tucker_tick` 三道闸（有登记 / WS 级绑定探测 / 差集判定）→ 标题路径优先，失败退回按登记基线做窗口差分。

## 四、安全

**现状（优点）**：本机 API 有 token（HttpOnly cookie）+ Host 白名单；配置敏感字段走 DPAPI 且
**读写两侧都清不可见字符**（v1.0.621）；`resolve_workspace_ref` 先 realpath 再判前缀 +
顶层黑名单 `系统/`（含 api_token）`组件/`，越界一律 404（`routes/workspace.py:165-195`，已读确认）；
产物库写入统一 `ws_rel_path()` 防穿越；OCR wheel 解压有 zip-slip 校验（`core/ocr.py:349-357`）。

**问题（高）**：**「绝不自动点同意/提交」这条业务红线仍然只在提示词层。**
证据：`security_ops.py:202-214` 的 `_ALWAYS_ASK` 只覆盖 `run_audit_flow(auto_approve)`；
`agent_tools/executors.py:786` 的 JS 危险名单只有 `\.submit\s*\(\s*\)`，**没有 `.click(` 与
`dispatchEvent`**；全项目 grep 不到任何按按钮文案（同意/提交/审批通过）设的拦截。
后果：`wecom_run_js("…querySelector('[data-btn=approve]').click()")` 在 auto 档或
`sched-`/`study-` 后台会话里可全程无审批执行——而这台机器驱动的是**有真实业务后果的财务单据**。
（源码确认；未做真实页面复现，因为那等于点审批按钮。）
修复方向（需你先定口径，会改变自动化行为，我不擅自动）：JS 名单补 `.click(`/`dispatchevent`；
给 click 类工具加"目标文案命中审批词 ⇒ 无论档位一律转人工"的闸门；配一条"审批词闸门必须存在"的锁。

**问题（中）**：`core/portable.py:548-557` 安装提交时 `shutil.rmtree(final)` 发生在
`_exe_candidates()` 校验**之前**——包结构哪天变了会先把现有可用运行时删光再报错。
修法：先校验新解压目录可执行，再原子换名；失败保留旧目录。（上轮 A5-2 原样仍成立。）
